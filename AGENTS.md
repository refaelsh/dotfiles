# Project Rules for AI Agents

1. Disregard the folder misc - it is an old historical leftover/backup.
2. Do not commit/push to the repo without my explicit permission.
3. This is my live NixOS config, please be very careful with it.
4. NEVER create a git commit (even locally) without the user explicitly saying "Please commit this" (or equivalent) in the current conversation. This is a *live* NixOS configuration running on the user's actual machine. Unauthorized commits risk putting untested, incomplete, or broken changes into the git history that could later be applied to the running system. Always treat commits as high-risk operations here.
5. When adding or modifying comments in configuration files, keep them self-contained and explain the reasoning directly in the comment itself. Never reference external documents, plans, sessions, scans, step numbers, or dates (e.g. "2026 perf scan", "see the plan", "A2", "H1"). Future readers (including the author a year later) will not have that context.
6. If you stage files (e.g. so Nix flakes can see untracked paths), unstage them when you finish the task (`git restore --staged …`). Leave changes as ordinary working-tree / untracked edits so a plain `git diff` (and status) is easy to review. Never leave a dirty index behind unless the user asked you to stage or commit.
7. Never add or keep a NixOS option from memory, old docs, or another machine's nixpkgs. This flake tracks `nixos-unstable`; options are renamed and removed often (`extraConfig` → `settings`, and similar). Before writing an option, confirm it exists **and is not `mkRemovedOptionModule` / `mkRenamedOptionModule`** in this flake's locked nixpkgs. Check by evaluating the option on `nixosConfigurations.myNixos` or by reading the module under that nixpkgs (e.g. grep the `nixpkgs` input for the option name). A rebuild that dies on "no longer has any effect" is a failure to check, not an acceptable first signal.
8. Do not remove a package from `environment.systemPackages` because you assume NixOS or another module already provides it. Check first: read the enabling module (does `programs.foo.enable` actually install that derivation?), and confirm the **same command** stays on PATH after the removal (e.g. `ssh` / `scp` come from the `openssh` **client** package, not from `services.openssh`, which is the server and is off here). A tool being a dependency of git or living in the nix store is not the same as it being on PATH. If the check is ambiguous, leave the package and ask.
